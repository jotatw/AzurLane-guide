# Roadmap

> Evolução planejada da Azur Lane Knowledge Base.

## Objetivo

O roadmap define a direção de crescimento do projeto sem transformar o desenvolvimento em uma lista rígida de funcionalidades.

A evolução ocorre por fases de maturidade. Uma fase deve fornecer uma base suficientemente consolidada antes que a próxima seja expandida.

## Princípio de Evolução

```text
Foundation
    ↓
Fundamentals
    ↓
Game Systems
    ↓
Knowledge Base
    ↓
Case Studies
    ↓
Personal Tools
    ↓
Website
```

A sequência representa uma direção, não uma obrigação de implementação completa.

---

# Fase 0 — Foundation

**Objetivo:** estabelecer a estrutura, os princípios e os métodos do projeto.

### Escopo inicial

- Visão do projeto.
- Filosofia.
- Metodologia.
- Terminologia.
- Glossário.
- Catálogo de fontes.
- Roadmap.
- Registro de questões.

### Resultado esperado

Uma base estável para receber conhecimento sem exigir reorganizações constantes.

---

# Fase 1 — Fundamentals

**Objetivo:** compreender os fundamentos de Azur Lane antes de iniciar análises avançadas.

### Possíveis áreas

- Interface e sistemas básicos.
- Recursos.
- Oil.
- Coins.
- Wisdom Cubes.
- Construção.
- Dock.
- Níveis e limites de nível.
- Skills.
- Equipamentos.
- Fleets.
- Campanha.
- Commissions.
- Daily e Weekly.
- Submarinos.
- Dorm.

### Resultado esperado

Uma compreensão suficiente dos sistemas básicos para que documentos posteriores possam assumir esse conhecimento sem repetir explicações fundamentais.

---

# Fase 2 — Game Systems

**Objetivo:** estudar os principais sistemas individualmente e compreender suas relações.

### Possíveis áreas

- Combat.
- Equipment.
- Research.
- Retrofit.
- Augment Modules.
- META.
- Hard Mode.
- Submarines.
- Operation Siren.
- Endgame.
- Outros sistemas permanentes relevantes.

### Resultado esperado

Conhecimento estruturado sobre como os sistemas funcionam, seus requisitos, custos, interações e limitações.

---

# Fase 3 — Knowledge Base

**Objetivo:** transformar o conhecimento acumulado em documentação prática e reutilizável.

### Possíveis áreas

- Progressão.
- Farming.
- Gerenciamento de recursos.
- Investimento.
- Fleet Building.
- Sinergia entre navios.
- Equipamentos.
- Mapas.
- Drops.
- Eficiência.
- Decisões de desenvolvimento.

### Resultado esperado

Documentação capaz de responder não apenas como um sistema funciona, mas quando e por que pode compensar utilizá-lo.

---

# Fase 4 — Case Studies

**Objetivo:** aplicar o conhecimento documentado em situações concretas.

Os estudos podem utilizar contas, fleets, testes ou situações específicas como exemplos práticos.

### Possíveis estudos

- Composição de Mob Fleet.
- Composição de Boss Fleet.
- Investimento em navios.
- Retrofits.
- Augment Modules.
- Equipamentos.
- Estratégias de farm.
- Mapas específicos.
- Testes de dano.
- Progressão de uma conta.

### Resultado esperado

Demonstrar como fatos, análises e recomendações são aplicados em contextos reais sem transformar uma situação específica em regra universal.

---

# Fase 5 — Personal Tools

**Objetivo:** criar ferramentas somente quando o conhecimento documentado demonstrar uma necessidade clara.

### Possíveis ferramentas

- Organização da coleção.
- Comparação de navios.
- Planejamento de investimentos.
- Fleet Builder.
- Verificação de sinergias.
- Planejamento de recursos.
- Acompanhamento de progressão.

### Regra

Ferramentas devem consumir conhecimento e dados já estruturados. A existência de uma ferramenta não deve determinar a estrutura da Knowledge Base.

### Resultado esperado

Ferramentas pequenas e úteis para apoiar decisões e organização da conta.

---

# Fase 6 — Website

**Objetivo:** transformar a Knowledge Base em uma interface visual e navegável quando houver conhecimento e dados suficientes para justificar isso.

### Possíveis funcionalidades

- Navegação pela documentação.
- Pesquisa.
- Consulta de navios.
- Consulta de equipamentos.
- Visualização de fleets.
- Organização da conta.
- Ferramentas desenvolvidas na fase anterior.

### Regra

O website é uma camada de apresentação e interação sobre o conhecimento existente. Ele não deve antecipar a necessidade de conteúdo ou ferramentas que ainda não foram consolidados.

### Resultado esperado

Uma interface simples que torne a documentação e as ferramentas mais fáceis de consultar e utilizar.

---

# Fase 7 — Evolução Contínua

Depois das fases iniciais, o projeto poderá evoluir conforme novas necessidades surgirem.

Possíveis extensões incluem:

- Novos sistemas do jogo.
- Novos conteúdos permanentes.
- Atualização de dados.
- Automação.
- Integração com APIs existentes.
- Novas ferramentas.
- Estudos especializados.

Essas extensões não são compromissos do projeto. Cada uma deve ser avaliada conforme os princípios da Foundation.

---

# Critérios de Evolução

Uma fase não precisa ser considerada completamente encerrada para que outra comece, mas deve existir uma base suficientemente consolidada para evitar que a nova fase gere complexidade desnecessária.

Antes de expandir uma fase, considerar:

- O conhecimento atual está suficientemente organizado?
- As fontes são conhecidas?
- Existem lacunas importantes?
- A nova etapa resolve uma necessidade real?
- A manutenção será sustentável?
- Já existe uma solução externa adequada?

---

# Regra Final

> **O roadmap orienta o crescimento; ele não obriga o projeto a crescer.**

Se uma fase anterior já resolver as necessidades atuais, não existe obrigação de avançar para a próxima apenas para aumentar o tamanho do projeto.
